Longer-term follow-up to dotfiles-187t / pickletown gt-o2jy (agent-only HTTPS transport, shipped in #25). Raised 2026-08-26: the human/interactive side already has the credential-helper half of this wired up unconditionally (~/.gitconfig.local, generated by gitconfig.sh, sets `credential.https://github.com.helper = !gh auth git-credential` whenever gh is installed) -- it's just unused today because interactive remotes are still git@github.com: (SSH). Adding `url."https://github.com/".insteadOf = "git@github.com:"` to the real global gitconfig would make HTTPS the default for every git operation on the machine, not just Claude Code agent sessions, and would fully close out gt-rv0z (pt track's SSH-preference bean) in the process.

Deliberately NOT done yet. Explicitly deferred as a separate, longer-term call -- especially sensitive on the work/Gusto side. Needs research before deciding, not just implementation.

## Known tradeoff already identified
Switching push auth from the SSH key (Touch ID / 1Password-gated, per commit) to `gh`'s OAuth token (silent, no per-push prompt) removes an interactive checkpoint on every push, everywhere -- not just headless/agent pushes. Commit *signing* is unaffected either way (local operation, still the 1Password-backed SSH signing key regardless of push transport).

## Research questions (work/Gusto context specifically)
- Does Gusto have any written policy or security requirement mandating SSH-key-based git auth specifically (vs. OAuth token auth) for pushes to Gusto-org repos? Check with Security (#security-help / security-grc@gusto.com per reference_security_grc_intake_routing) if it's unclear from existing docs.
- Is `gh`'s OAuth token itself SAML-SSO-authorized per-org the same way SSH keys are? `claudeconfig.sh`'s agent-identity validator already confirms the *SSH key* is SSO-authorized for Gusto and guideline-app (see ADR 0031 checks) -- but that's a different credential. If the OAuth token isn't independently SSO-authorized (or needs separate per-org authorization clicked in GitHub), switching push auth over would need that confirmed first, or work pushes would start failing.
- Any Gusto audit-trail / compliance expectation that ties push provenance to a specific SSH key fingerprint (e.g. for SOC2 evidence, key-rotation policy, or incident response) that an OAuth-token-based push would break or complicate?
- Are there other engineers/teams at Gusto with an established stance on this (HTTPS-vs-SSH for git) worth checking before changing a personal default that also touches Gusto-org repos?
- Does this interact at all with existing SSH-agent-key infra (ADR 0030/0031/0033) in a way that matters, or is it purely additive (existing 1Password-agent-socket SSH flow keeps working as a fallback/alternative regardless)?

## Possible outcomes
- Clean to do globally: add the `insteadOf` to the real `~/.gitconfig`/gitconfig.sh output, simplify the two agent-role fragments to drop their own now-redundant `insteadOf`/credential blocks (they'd inherit via `[include] path = ~/.gitconfig`).
- Work-side has a real constraint: scope to `home` role only (personal repos), leave `work` role/interactive Gusto pushes on SSH.
- No clean answer either way: leave as-is (current agent-only state), re-visit if/when `gt-rv0z` resurfaces as active pain.

## Resolution (2026-08-27)
Implemented the "home role only" outcome: `gitconfig.sh` now adds `url."https://github.com/".insteadOf = "git@github.com:"` to `~/.gitconfig.local`, gated on `DOTPICKLES_ROLE=home` specifically (not the shared home/container/claude-code-remote/coi-host block). `work` role is untouched -- still SSH, since the Gusto policy/SSO research questions above were never answered, just avoided by not touching that role.

Also updated the stale comment in `home/.gitconfig.d/claude-agent-home` (dotfiles-187t) that claimed "your interactive shell keeps using SSH normally" -- no longer true for home role, though that fragment is kept for agent sessions regardless so they don't depend on the interactive config.

Signing is unaffected as anticipated: still goes through 1Password's `op-ssh-sign` SSH key, unrelated to push/fetch transport.

Verified: `git remote -v` on this repo now shows `https://github.com/...` and `git ls-remote` succeeds via `gh`'s credential helper.

If work-role SSH-vs-HTTPS ever comes up again, the unanswered Gusto research questions above still apply -- this bean's research was bypassed by scoping narrowly, not resolved.
