# Editing `claude/` (Claude Code's own config)

[claude/README.md](../../claude/README.md) covers the architecture: roles, stacks, how merging works, permission syntax. This file covers the conventions that aren't obvious from reading it.

## Pick the Right Rules Directory

Two directories, different scopes. They are easy to confuse because the names differ by one dot.

| Directory        | Installs to        | Loads in           | Use for                                       |
| ---------------- | ------------------ | ------------------ | --------------------------------------------- |
| `claude/rules/`  | `~/.claude/rules/` | **every repo**     | knowledge that travels (tooling, OS behavior) |
| `.claude/rules/` | nowhere, read here | **this repo only** | how to work on dotfiles itself                |

**How to apply:** ask "would this help me in an unrelated repo?" If yes, `claude/rules/`. If it's about editing files in this repo, `.claude/rules/`. Scope a project rule to the files it concerns with `paths:` frontmatter, as a YAML list of globs:

```yaml
---
paths:
  - 'claude/**'
---
```

A rule with no `paths` loads unconditionally. A `paths` list that matches nothing means the rule never loads at all, so a typo here fails silently in the worst direction.

## Match the House Style in `claude/rules/`

Each rule is a directive, not a reference page: `## Heading` stating the rule, a `**Why:**` paragraph, then `**How to apply:**` bullets. Lead with the instruction and put the mechanism underneath.

**Why:** these files load into context in every session, in every repo. Length is a real cost, and a rule buried three paragraphs into background gets skimmed past. `worktrees.md` is 12 lines and `taskwarrior.md` is 32; treat those as the target, not the floor to build up from.

**How to apply:**

- Only `##` headings. No `###` nesting, which is a sign the file is turning into a wiki page.
- Cut background that doesn't change what you'd do. Link to the ADR for the full story.
- Reach for a [skill](https://code.claude.com/docs/en/skills) instead when it's a multi-step procedure. Skills load on demand; rules cost context every session.

## Applying Changes

Rules and `CLAUDE.md` reach `~/.claude/` through a **directory symlink**, so edits are live immediately with no regeneration step.

`settings.json` is different: it is generated by `./claudeconfig.sh` from `roles/` plus `stacks/`, and needs a re-run. That script needs `dangerouslyDisableSandbox` for its final write to `~/.claude/settings.json`, which is a protected path no `allowWrite` entry can exempt. Everything else in it runs sandboxed. Settings edits apply to the running session, so no Claude Code restart.

Never hand-edit under `~/.claude/` -- `claudeconfig.sh` overwrites it.

## `claude/rules/` Is in the Sandbox Deny List

Writes there EPERM from Bash-side tools, even though the Edit and Write tools handle it fine. `bin/prettier --write` fails, which also means the lefthook pre-commit hook fails on any staged rules file needing reformatting.

**How to apply:** re-run that one command with the sandbox off. Tracked as `dotfiles-3vm4`.
